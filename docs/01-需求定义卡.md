## B. Skill 需求定义卡

### 1. Skill 中文展示名称

**机器人仿真实机参数错配诊断器**

细分场景：机器人仿真与实机之间；核心动作：参数错配诊断；定位：器/工具。
共 14 个汉字（在 8—15 区间内），不含版本号，不是泛化命名。

### 2. Skill 英文标识

`ros2-sim-hw-mismatch-auditor`

- 仅小写字母、数字、连字符；
- 28 个字符（<=64）；
- 不以连字符开头/结尾，无连续连字符；
- 与 Skill 目录名完全一致。

### 3. 目标用户

- 做差速底盘/移动机器人课程的本科生、研究生；
- 刚接手别人 ROS 2 工程、需要快速确认参数是否自洽的开发者；
- 被“仿真对、实车不对”卡住的嵌入式/控制方向工程师。

### 4. 对应赛道方向

赛道一「开源基础软件与解决方案」，类别 2「AI 开发工具链与智能体框架」。
交付物是**开源软件 + Agent Skill**，而不是提示词或文档。

### 5. 关键词和价值点

关键词：ROS 2、URDF、参数一致性、里程计标定、差速运动学、根因定位、可复现证据。

价值点（都可验证）：

1. 把“翻十几个文件找数值”压缩成一条命令、几秒钟；
2. 每条结论都带文件:行号与原文，不用相信工具的口头结论；
3. 运行偏差与静态冲突互相印证，给出**唯一**修正值；印证不上时明确说“不确定”；
4. 生成可直接 review 的 unified diff，改前自动备份；
5. 全流程写调试痕迹（JSONL），别人可以照着复现同一次判定。

### 6. 真实使用场景

- 学生做完 Gazebo 仿真，上实车后发现直行 1 m 只记 0.98 m；
- 移植 ROS 1 工程，配置里残留毫米单位；
- 改了 params.yaml 没生效，实际是 launch 覆盖或同键重复；
- 交接代码，想确认 URDF 几何、配置、源码常量是否一致；
- PID 调不出来，需要先分清是参数错、周期抖还是通信延迟。
### 7. 用户输入

- 一个 ROS 2 工程目录（.urdf/.xacro、.yaml/.yml、*.launch.py/*.launch.xml、.cpp/.hpp/.py）；
- 可选：一份运行日志（CSV 带表头，或逐行 key=value / ROS 2 控制台文本）；
- 可选：实测真值（日志里的 truth_x/truth_y/truth_yaw，或 `--expect-distance` / `--expect-yaw`）。

### 8. Skill 输出

| 产物 | 说明 |
|---|---|
| report.md | 中文报告：结论摘要 / 输入指纹 / S·R·C 三类发现 / **未验证项** / 已通过项 / 复现命令 |
| findings.json | 机器可读，含 rule、severity、confidence、status、evidence、proposals、metrics |
| trace.jsonl + trace.md | 逐条调试痕迹（阶段、动作、规则、读取的文件、判定结果） |
| patches/*.patch | 针对具体行的 unified diff（默认不落盘） |

### 9. 标准工作流程

1. 扫描工程，识别文件类型，逐文件记录读取行为到 trace；
2. 解析 URDF/Xacro（含多行标签与表达式）、YAML（含 flow 列表每个元素列号）、launch、源码常量；
3. 把每个字面量映射到规范参数名（别名表 + 直径→半径折算），记录文件/行/列；
4. 跑 S01—S10 静态规则，输出冲突、单位、几何、惯量、频率、限速、重复键等问题；
5. 若有日志：解析列名同义词，跑 R01—R08 运行规则；
6. 交叉验证：R01 × S01/S02/S10 → C01，R02 × S04 → C02；只有反推值能与工程内另一处字面量吻合才定根因；
7. 生成补丁（按行列定位，只改数值字面量）；
8. 写 report.md / findings.json / trace.*，控制台输出摘要；
9. 用户确认 diff 后可用 `--apply` 落盘（自动生成 .bak）。

### 10. 触发词

仿真和实物对不上、机器人走不准、里程计不准、排查参数、轮子半径写错、轮距不对、
调参调不出来、检查 urdf 和 params、日志分析一下、帮我看看为什么转弯角度不对
（共 10 个，含书面指令与口语表达）

### 11. 结果验收标准

1. 每条结论能定位到**具体文件 + 行号 + 原文**（自动测试逐字核对 20+ 条证据）；
2. 能在分钟级给出结论（示例工程 5 个文件 + 250 行日志，全流程 < 1 秒）；
3. 全流程有可复现痕迹（trace.jsonl，序号严格递增）；
4. 反推修正值必须与工程内已有字面量吻合（容差 0.5%）才给 HIGH 置信度，否则降级或判 unverifiable；
5. 对照工程（参数完全一致）必须零发现，不误报。

### 12. 不应该做什么

- 不臆造参数：文件里没读到就不存在；
- 不编造测试通过：没跑过的检查不写“已通过”；
- 不在缺真值时给绝对偏差数字；
- 不在多个数学等价解释之间替用户随便选一个；
- 不夸大能力（不写“全自动修复所有问题”）；
- 不设计无关功能（不做商业计划、不做未来扩展、不做感知/导航算法）；
- 不自动改用户代码（除非显式 `--apply`）。

## 【项目核心功能】

只做完成作品所必需的四件事：

1. **多源参数提取与规范化**（URDF/YAML/launch/源码 → 规范参数名 + 行列证据）；
2. **静态一致性规则 S01—S10**；
3. **运行日志规则 R01—R08**（尺度、抖动、延迟、饱和、超调、死信号、数据质量）；
4. **交叉验证 C01—C02 + 补丁 + 报告 + 调试痕迹**。

不做：GUI、数据库、Web 服务、多机协同、SLAM/导航、模型训练。

## 【技术实现方式】

| 需要的能力 | 实现方式 | 依赖 |
|---|---|---|
| 带行列号的 XML 解析 | 自研 tokenizer（正则 + 位置映射），支持多行标签与注释 | 标准库 re |
| YAML 解析（要列号） | 缩进感知的逐行扫描器，支持嵌套映射、flow 序列（每元素列号）、块序列、注释剥离 | 标准库 re |
| launch 解析 | 针对 DeclareLaunchArgument、参数字典、ParameterValue、XML param 的定向正则 | 标准库 re |
| 源码常量解析 | constexpr / #define / Python 赋值三类模式 + 别名过滤（避免把 i = 0 当参数） | 标准库 re |
| 日志解析 | CSV/分隔符嗅探、key=value 提取、ROS 2 控制台时间戳提取、列名同义词表 | 标准库 csv |
| 积分/弧长/解缠/互相关 | 梯形积分、轨迹弧长、角度解缠、归一化互相关时延估计 | 标准库 math |
| 补丁生成 | 基于行列定位的字面量替换 + difflib.unified_diff | 标准库 difflib |
| 追溯 | 每次动作追加一行 JSONL | 标准库 json |
| 测试 | pytest，56 个用例 | 开发期 pytest（非运行时依赖） |

代码规模：`scripts/rswaudit/` 12 个模块 + 1 个入口脚本，约 3500 行 Python（含注释与文档字符串），
测试代码 642 行，运行时零第三方依赖。
